# Attachments design

Date: 2026-09-28
Status: approved in conversation, awaiting implementation

Supersedes the data model in
[`2026-09-28-image-upload-field-design.md`](2026-09-28-image-upload-field-design.md)
and its plan. The component, the route handler and the Blob store in those
documents still stand; what changes is where the address is kept.

## Goal

Replace the three inline image URL columns with one `attachments` table, so a
story, a session or a scene can carry several pictures, each one knowing
whether it is a link someone typed or a file this app uploaded, and each one
moving through a status workflow while it uploads.

## Scope

In scope:

- `attachments_kind` enum and the `attachments` table, registered with
  `_tables` and mapped to a new status workflow.
- Two triggers: one that proves an attachment's parent exists, one attached to
  all three parents that deletes their attachments with them.
- A one-time migration that moves `stories.image_url`,
  `story_sessions.image_link` and `story_scenes.image_link` into rows, drops
  the columns, and recreates `v_story_scenes` without `image_link`.
- The Drizzle mirror, the attachment server actions, and the uploader rewired
  to create and claim rows.
- The three forms attaching pictures as a list rather than one field.
- The sweep extended to unclaimed attachments.

Out of scope (later work): attachments that are not images (handouts, maps,
audio), reordering the list by drag, and thumbnails or transformation. The
`sort_order` column exists so ordering does not need a migration later, but
nothing writes it beyond append order.

## Why a table rather than more columns

Three columns meant three shapes for the same idea and one picture per object.
A table gives every kind the same treatment, lets a scene carry several
pictures, and — because a row exists before its bytes do — makes an upload a
thing with a state rather than an event that either happened or did not. A
blob with no `READY` row pointing at it is then definitively rubbish, which is
what makes the sweep safe to run.

## Schema

### The enum and the table (`db/custom/create_attachments_table.sql`)

The `kind` column is **not** declared here. `_p_update_tables()` builds it, and
its enum type, from values declared in `_tables` — see the registration below.

```sql
CREATE TABLE IF NOT EXISTS attachments (
    id_attachment integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    external_id   integer,
    status        varchar NOT NULL DEFAULT 'UPLOADING',
    url           text,
    is_uploaded   boolean NOT NULL DEFAULT FALSE,
    file_name     text,
    content_type  varchar,
    byte_size     bigint,
    sort_order    integer,
    CONSTRAINT attachments_ready_has_url CHECK (status <> 'READY' OR url IS NOT NULL)
);
```

`kind` is `NOT NULL` and `external_id` is not. A create form always knows it is
making a scene picture; what it does not yet know is which scene, because the
scene does not exist until the form is submitted. Keeping `kind` mandatory is
what lets the delete trigger match a detached row and what makes an unclaimed
row identifiable rather than anonymous.

The metatable was changed for this table and the work is **already done and
applied**: `_p_update_tables()` now reads `kind_column` from `_tables` instead
of scanning for any enum-typed column, and `_p_update_tables_kinds()` builds
the column and its type from declared `kind_values`. The old scan raised
*"query returned more than one row"* as soon as a table had two enum columns,
which would have stopped `attachments` ever having both a `kind` and an enum
`status`. `is_uploaded` is a boolean because it is two-valued, not because an
enum would break anything.

That path has been exercised against this database on scratch tables — a kind
built beside an unrelated enum, an enum extended by declaration, and a
mis-typed kind column refused — so `attachments` is not the first thing to
try it. Still worth confirming after the create migration that `_tables` holds
`kind_column = 'kind'` and the three `kind_values`.

`url` is null while the row is `UPLOADING`; the CHECK is what makes `READY`
mean the address exists. `is_uploaded` records intent at write time rather
than being re-derived from the URL, so a change of Blob domain cannot silently
turn our own files into other people's.

### Metatable registration

One call, using `_p_set_and_update_table_features()` — the whole `_tables`
setup rather than the dozen statements `create_story_sessions_table.sql`
spells out by hand:

```sql
CALL _p_set_and_update_table_features('attachments',
    p_timestamps          := TRUE,
    p_user_ids            := TRUE,
    p_activity_log        := TRUE,
    p_status_workflow_ids := ARRAY[-3],
    p_kind_values         := ARRAY['STORY', 'STORY_SESSION', 'STORY_SCENE']);

-- _p_update_tables_kinds() adds the column nullable, as it must for a table
-- that might already hold rows. Every attachment has a kind from the start.
ALTER TABLE attachments ALTER COLUMN kind SET NOT NULL;
```

That registers the table, declares the flags, builds `created_at` /
`updated_at`, the user id columns and their foreign keys, `activity_log`, the
`kind` column with its `attachments_kind` enum, then the whole status workflow,
and finishes with the foreign-key indexes. It raises if `attachments` is
missing from `_tables` afterwards, or if workflow -3 has not been seeded, so
the guards the older create scripts write out by hand come for free.

The enum type is `attachments_kind` — `<table>_<column>`, derived rather than
singularised, because turning `stories` into `story` in SQL needs rules that
break on the first irregular name.

`p_activity_log` is not optional here: the status transition trigger appends
every move to `activity_log` and expects to find it.

The uploader is `id_created_by_user`. No second user column.

### Workflow (`-3`, the next lowest; -1 and -2 are taken)

`seeds/seed_s_status_workflows.sql`:

```sql
(-3, 'Attachments Status Workflow', 'status', NULL)
```

`seeds/seed_s_statuses.sql`, with each row listing the statuses that may move
**into** it:

```sql
-- Attachments: UPLOADING -> READY or ERROR; ERROR -> UPLOADING (retry)
(-3, 'UPLOADING', 'The file is being uploaded.',            ARRAY['ERROR']),
(-3, 'READY',     'The file is stored and can be shown.',   ARRAY['UPLOADING']),
(-3, 'ERROR',     'The upload failed and may be retried.',  ARRAY['UPLOADING'])
```

`UPLOADING` lists only `ERROR` because the only *transition* into it is a
retry. Rows arrive in it by insert, and inserts are never checked: the
transition trigger is `BEFORE UPDATE` only. That is also what lets a typed
link be inserted straight into `READY` without pretending to upload
something.

### Trigger: the parent must exist

```sql
CREATE OR REPLACE FUNCTION tr_attachments_external_exists() RETURNS trigger AS
$$
DECLARE
    parent_table TEXT;
    parent_key   TEXT;
    found        BOOLEAN;
BEGIN
    -- A detached row is legal: a create form uploads before its story,
    -- session or scene exists, and claims the row when it is saved.
    IF NEW.external_id IS NULL THEN
        RETURN NEW;
    END IF;

    CASE NEW.kind
        WHEN 'STORY' THEN parent_table := 'stories'; parent_key := 'id_story';
        WHEN 'STORY_SESSION' THEN parent_table := 'story_sessions'; parent_key := 'id_story_session';
        WHEN 'STORY_SCENE' THEN parent_table := 'story_scenes'; parent_key := 'id_story_scene';
    END CASE;

    EXECUTE format('SELECT EXISTS (SELECT 1 FROM %I WHERE %I = $1)', parent_table, parent_key)
        INTO found USING NEW.external_id;

    IF NOT found THEN
        RAISE EXCEPTION 'attachments.external_id % has no % row', NEW.external_id, parent_table;
    END IF;

    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE OR REPLACE TRIGGER tr_biu_attachments_external_exists
    BEFORE INSERT OR UPDATE OF kind, external_id ON attachments
    FOR EACH ROW EXECUTE FUNCTION tr_attachments_external_exists();
```

A `CASE` with no `ELSE` raises on an unhandled enum value, which is the right
answer: a kind added to the enum and not to this function should fail loudly
the first time it is used, not attach to nothing.

### Trigger: one function, three parents

`OLD` has a different primary key name on each parent, so the function cannot
name it directly. It takes the key name as its second argument and reads the
value out of the row generically:

```sql
CREATE OR REPLACE FUNCTION tr_attachments_delete_for_parent() RETURNS trigger AS
$$
BEGIN
    DELETE FROM attachments
    WHERE kind = TG_ARGV[0]::attachments_kind
      AND external_id = (to_jsonb(OLD) ->> TG_ARGV[1])::integer;
    RETURN OLD;
END;
$$ LANGUAGE plpgsql;
```

```sql
CREATE OR REPLACE TRIGGER tr_ad_stories_attachments
    AFTER DELETE ON stories
    FOR EACH ROW EXECUTE FUNCTION tr_attachments_delete_for_parent('STORY', 'id_story');

CREATE OR REPLACE TRIGGER tr_ad_story_sessions_attachments
    AFTER DELETE ON story_sessions
    FOR EACH ROW EXECUTE FUNCTION tr_attachments_delete_for_parent('STORY_SESSION', 'id_story_session');

CREATE OR REPLACE TRIGGER tr_ad_story_scenes_attachments
    AFTER DELETE ON story_scenes
    FOR EACH ROW EXECUTE FUNCTION tr_attachments_delete_for_parent('STORY_SCENE', 'id_story_scene');
```

The kind and the key name arrive through `TG_ARGV` rather than being derived
from `TG_TABLE_NAME`, which would mean singularising `stories` into `STORY` in
SQL and would put the mapping inside the function — so adding a kind would
mean editing the function as well as attaching the trigger. This way the
function is written once and never touched again.

Deleting rows rather than cascading is deliberate: `external_id` is not a real
foreign key, so Postgres has no cascade to offer. The blobs those rows point
at are left to the sweep, which is the only thing that talks to Blob.

### Index

```sql
CREATE INDEX IF NOT EXISTS attachments_kind_external_id_idx
    ON attachments (kind, external_id);
```

Written by hand because `_p_update_fk_indexes` only indexes real foreign keys,
and every read of this table is "the attachments of this object".

## Data migration (one-time, `just new move_image_urls_to_attachments`)

Forward-only and idempotent, in this order:

1. **Backfill.** One insert per source table, skipping nulls and blanks, and
   skipping anything already moved so a re-run is harmless:

```sql
INSERT INTO attachments (kind, external_id, status, url, is_uploaded, sort_order,
                         id_created_by_user, id_updated_by_user)
SELECT 'STORY', s.id_story, 'READY', s.image_url, FALSE, 0,
       s.id_created_by_user, s.id_updated_by_user
FROM stories s
WHERE s.image_url IS NOT NULL
  AND btrim(s.image_url) <> ''
  AND NOT EXISTS (SELECT 1 FROM attachments a
                  WHERE a.kind = 'STORY' AND a.external_id = s.id_story);
```

   and the same for `story_sessions` / `STORY_SESSION` and `story_scenes` /
   `STORY_SCENE`. Every migrated row is `is_uploaded = FALSE`: Vercel Blob has
   never been wired up, so every URL in the database today is a link someone
   typed.

2. **Recreate the view.** `v_story_scenes` selects `image_link`, so it is
   recreated without that column in the same migration. Not `DROP ... CASCADE`:
   the dependants are found first and rebuilt deliberately. Check for other
   dependants before writing this step —
   `SELECT * FROM _tables WHERE 'story_scenes' = ANY(primary_key_dependants)`
   and the usual `pg_depend` walk.

3. **Drop the columns.**

```sql
ALTER TABLE stories        DROP COLUMN IF EXISTS image_url;
ALTER TABLE story_sessions DROP COLUMN IF EXISTS image_link;
ALTER TABLE story_scenes   DROP COLUMN IF EXISTS image_link;
```

   `story_scenes.search_text` is generated from status, title and description
   only — the column comment says the picture is deliberately excluded — so the
   generated column does not need rebuilding. Confirm that before dropping.

## Drizzle mirror

`attachments` as a `pgTable` in `schema.ts` with the audit columns declared the
standard way, a `relations()` block at the bottom of the file, and
`imageUrl` / `imageLink` removed from `stories`, `storySessions` and
`storyScenes`. `kind` is `varchar` on the Drizzle side with a TypeScript union
for its values; the enum lives in the database and `s_statuses` remains the
only source of truth for `status`, which stays a bare `varchar` here for the
same reason it is one on `story_scenes`.

New view type in `src/lib/attachments.ts`:

```ts
export type AttachmentKind = "STORY" | "STORY_SESSION" | "STORY_SCENE";

export type Attachment = {
  idAttachment: number;
  kind: AttachmentKind;
  externalId: number | null;
  status: string;
  url: string | null;
  isUploaded: boolean;
  fileName: string | null;
};
```

## Data access

`src/components/uploads/actions.ts`, all with the `sa_` prefix and
`requireUser()` first:

- `sa_createAttachment({ kind, externalId, url, fileName, contentType,
  byteSize })` — inserts the row, returning `{ idAttachment, status }`.
  `externalId` is null on a create form. Passing a `url` means a typed link,
  which arrives `READY`; omitting it means an upload is about to start, and
  the row arrives `UPLOADING` with `is_uploaded = TRUE` and no address yet. When `externalId` is given, the caller's right to attach to that
  parent is checked the same way the board's reads check it, by proving the
  story is theirs; the exists-trigger is a backstop, not the authorisation.
- `sa_markAttachmentReady(idAttachment, url, meta)` — `UPLOADING -> READY`.
- `sa_markAttachmentError(idAttachment)` — `UPLOADING -> ERROR`.
- `sa_retryAttachment(idAttachment)` — `ERROR -> UPLOADING`.
- `sa_deleteAttachment(idAttachment)` — deletes the row, and the blob too when
  `is_uploaded`, guarded by `isUploadedBlobUrl()` as a second check.
- `sa_listAttachments(kind, externalId)` — `READY` and in-flight rows for one
  object, ordered by `sort_order` then `id_attachment`.
- `sa_claimAttachments(kind, externalId, ids)` — see below.

Every one of these refuses a row whose `id_created_by_user` is not the caller,
except the reads, which prove ownership through the parent story.

### Claiming

The create actions (`sa_createStory`, and the scene and session equivalents)
take the attachment ids the form collected and claim them after inserting the
parent, inside the same transaction:

```sql
UPDATE attachments
SET external_id = $newParentId, id_updated_by_user = $callerId, updated_at = NOW()
WHERE id_attachment = ANY($ids)
  AND kind = $kind
  AND external_id IS NULL
  AND id_created_by_user = $callerId;
```

All four conditions carry weight. Without `external_id IS NULL` a caller could
re-point an attachment already sitting on someone else's scene; without
`id_created_by_user` they could claim one they never uploaded; the `kind`
match stops a story picture being claimed as a scene's. A claim that matches
nothing is ignored rather than raised: a double-submitted form should not
fail, and there is nothing the user could do about it if it did.

## The uploader

`ImageUploadField` keeps its shape from the superseded spec — dropzone, typed
URL, preview, the three states — and becomes a list rather than one value. The
sequence for an upload is now:

1. `sa_createAttachment(kind, externalId, { fileName, contentType, byteSize })`
   returns an id, status `UPLOADING`.
2. `upload()` sends the bytes browser-direct, keyed
   `uploads/<user-id>/<filename>` as before.
3. `sa_markAttachmentReady(id, blob.url, …)` on success, or
   `sa_markAttachmentError(id)` on failure, which leaves a visible row with a
   Retry button rather than a picture that silently never appeared.

A typed URL is one call: `sa_createAttachment` with the URL, straight to
`READY`.

`externalId` is null on a create form and the real id on an edit form; nothing
else about the component differs between the two, which is the point of
letting the column be null.

## The sweep

Two passes now, both with the same 24-hour grace period:

1. **Unreferenced blobs** — as before, except the referenced set is now one
   query: `SELECT url FROM attachments WHERE is_uploaded AND url IS NOT NULL`.
   Simpler and cheaper than reading three tables.
2. **Unclaimed attachments** — rows with `external_id IS NULL` older than 24
   hours are deleted, and their blobs with them. These are create forms
   someone abandoned.

The grace period is what makes both safe: a row uploaded into a form that has
not been submitted is unclaimed and unreferenced, and deleting it would take
the picture out from under someone mid-edit.

## Forms

`storySchema` loses `imageUrl` entirely — pictures no longer travel as a form
field. The story, session and scene forms each render the attachment list and
post the ids they collected, and the create actions claim them.

The story card reads its picture from the attachments of the story rather than
a column. The protocol pin that kept `javascript:` and `data:` out of the CSS
`url("…")` sink moves with it: it now lives on the attachment schema, and the
card still encodes the value. Both halves are still needed.

## Error handling

Inline, never toasted. An upload that fails leaves an `ERROR` row with its
file name and a Retry button; nothing disappears silently. A delete that the
database refuses is reported inline, because unlike the blob-only case there
is now a visible row that did not go away, and saying nothing would leave the
user looking at something they asked to remove.

## Tests

Action tests hit the real database and are skipped without `DATABASE_URL`,
create their own fixtures and clean up in both `before` and `after`.

- The exists-trigger refuses an `external_id` with no parent row, and allows a
  null one.
- Deleting a story, a session and a scene each removes that object's
  attachments and leaves the other kinds alone.
- `UPLOADING -> READY`, `UPLOADING -> ERROR` and `ERROR -> UPLOADING` are
  allowed; `READY -> UPLOADING` is refused by the transition trigger.
- The CHECK refuses a `READY` row with no URL.
- Claiming ignores an id belonging to another user, one already attached, and
  one of the wrong kind, and attaches the rest.
- `sa_deleteAttachment` refuses another user's row.
- The sweep deletes an unclaimed row older than the grace period and keeps a
  fresh one.
- Component tests as in the superseded spec, plus: an `ERROR` row renders a
  Retry button, and a create form collects ids without an `externalId`.
- After the first migration, `_tables` holds `kind_column = 'kind'` and the
  three `kind_values`.
